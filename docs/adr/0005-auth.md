## 状态

Accepted · 2026-10-20

## 背景

`niucode` 已经有 OpenAI-compatible provider，但每次都要在命令行里传 `DEEPSEEK_API_KEY`，体验差且容易把 key 写进 shell history。目标是让 API key 像登录一样只配置一次。

同时要避免两个错误方向：

- 把 DeepSeek / ChatGPT 的网页 cookie 当作 API；这不稳定、违反服务条款，也会把会话凭证暴露给 harness。
- 把 key 直接写进仓库配置或 session 事件；日志会被分享、提交、回放。

## 决策

新增独立 `niucode-auth` crate，统一解析凭证：

```text
环境变量
  ↓ 没有
OS keyring（service = "niucode", account = provider）
  ↓ 不可用
0600 credentials.toml
```

- 环境变量优先，方便 CI 和临时覆盖。
- keyring 可用时写入 OS keychain / Credential Manager / Secret Service。
- keyring 不可用时回退文件；Unix 上文件 `0600`，目录新建时 `0700`。
- `niucode auth status` 只显示来源，不打印 key；文件权限过宽时提示 `insecure`。
- `niucode auth unset` 同时清理 keyring 和文件。
- Provider 不直接读环境变量；入口（CLI，未来 loop）通过 `niucode-auth` 拿 key。
- 不支持网页账号 cookie；ChatGPT 账号 OAuth（SIWC）是独立项目，不在本 ADR 范围。

## 后果

### 正向

- 一次 `niucode auth set deepseek` 后，`niucode provider test` 和后续 loop 都不需要重复传 key。
- 密钥不会进入 session JSONL、日志或 `Debug` 输出。
- 无桌面环境仍然可用；keyring 失败不会阻塞。
- provider 保持凭证无关，便于未来接入不同 auth 方式。

### 负向

- Linux keyring 依赖 Secret Service / DBus；构建需要 `libdbus-1-dev`，最小容器需要设置 `NIUCODE_AUTH_DISABLE_KEYRING=1`。
- 文件回退仍是明文（0600），无法防御同用户恶意进程。
- 目前没有 zeroize；key 在进程生命周期内存在。
- 每个入口都必须记得使用 `niucode-auth`，否则会出现第二套读取逻辑。

## 备选方案

- **只读环境变量**：最简单，但每次都要配置，容易进 shell history。
- **只写文件**：跨平台简单，但桌面用户失去 keychain 的保护。
- **网页 cookie / 浏览器自动化**：不做；安全与稳定性都不可接受。
- **ChatGPT 账号 SIWC**：官方能力，但需要 OAuth + Responses API 和开源许可，作为后续独立 ADR。

## Revisit 条件

1. ChatGPT SIWC 正式接入，需要新的 OAuth 凭证类型。
2. 需要多用户/多租户，keyring 的 per-user 模型不够。
3. 需要 zeroize 或硬件密钥（YubiKey/Passkey）。
