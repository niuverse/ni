## 状态

Accepted · 2026-10-20

## 背景

项目看板最初照搬了任务看板的默认视图：打开就是 Board、里程碑进度条、完成率和卡片计数。这个结构回答的是"做到哪了"，但项目真正需要反复阅读的是"系统由哪些边界组成、依赖往哪流、为什么这样切"。

进度信息还有两个问题：它和 git、session log 重复；为了看起来完整，会诱导维护者不断更新百分比和统计数字，而不是更新架构和决策。卡片本身仍然是 agent 的 handoff 面，值得保留，但不应该占据第一屏。

## 决策

1. **默认视图改为 Architecture**，导航固定为 Architecture / Work / Docs / Decisions。
2. **Work 降为二级视图**：保留卡片、状态列和里程碑筛选，但移除进度条、完成率、WIP 数字和卡片计数。
3. **Architecture 只保留结构信息**：层、模块、关系、owned paths、contract、源码；`planned / active / done` 是模块状态，不是完成率。
4. **Decisions 只收决策**：ADR 和 `kind = "decision"` 事件；不展示"某张卡完成"的流水账。
5. **不上前端框架**：继续原生 JS/CSS，保持单文件、离线、`cargo xtask dashboard` 确定性构建。
6. **视觉方向为 technical field guide**：暖纸、墨色、深绿强调、低饱和层色；架构图是主角；不做 zoom/pan 和拖拽编辑。

## 后果

### 正向

- 第一屏直接回答"系统长什么样"，而不是"完成了几张卡"。
- 进度回到 git / session log / Work 视图，减少看板变成第二真相源的压力。
- 单文件、零构建、离线可用；页面大约维持在当前体量。
- 模块聚焦会弱化无关节点，复杂架构图仍然可读。

### 负向

- 想快速看进度的人需要多点一次 Work。
- 卡片状态仍然需要维护；只是不再用进度条装饰它。
- 没有 zoom/pan，超过约 30 个模块后需要重新评估图导航。

## 备选方案

- **保留 Board 优先**：改动最小，但与架构阅读的目标冲突。
- **删除 Work，进度交给 GitHub Issues**：最纯粹，但会破坏当前 `AGENTS.md` 依赖卡片做 handoff 的流程，并引入第二套状态源。
- **引入 React/Svelte + 图编辑器**：当前 9 个模块、8 条关系，框架 runtime 比数据还大；等真的需要编辑/拖拽/多人协作时再做。

## Revisit 条件

出现以下任一情况时重新评估：

1. 模块数量超过 30，或关系超过 60，当前分层图不可读。
2. 需要在浏览器里编辑架构或卡片，而不只是阅读。
3. 出现多个并发读者/写者，需要真正的服务端状态。
